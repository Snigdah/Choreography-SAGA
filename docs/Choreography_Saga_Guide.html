01Saga basics

A fund transfer touches several services, and each one has its own database. A single database transaction cannot cover all of them, so the work is split into local steps that are linked by events.

A Saga is that chain of local steps. Each service commits its own change, then publishes an event saying what happened. The next service reacts to that event.

In a choreography Saga there is no central coordinator. No service calls another service. Each service only listens to Kafka topics and decides for itself what to do next.

If a step fails, earlier steps cannot be rolled back with a database rollback, because they are already committed in other databases. Instead, the failing service publishes a failure event, and the services that already did work run a compensating action: a new business transaction that undoes the effect. For example, GL never deletes a journal. It books a new reversal journal with debit and credit swapped.

Five rules this POC follows

#RuleWhy it matters
1Services talk only through Kafka events.No service knows the URL of another. A slow or stopped service does not block the others.
2Each service owns its own database.Transaction Engine cannot read or update gl_journal. It learns about GL only from GL events.
3flowType travels in every event.Both scenarios start with the same event. SEQUENTIAL or PARALLEL tells each service whether to react.
4Rollback is a new action, never a delete.GL posts a REVERSAL journal. Account sets the reservation to RELEASED. The audit trail stays complete.
5The transactionRef is the Kafka message key.All events for one transfer land on the same partition, so they are processed in order.

03Topics and events

There is one topic per publishing service. A service writes only to its own topic and reads from the topics of the services it cares about.

Note

Topics are created by the applications, not by Docker. At startup each service lists the existing topics, creates only the missing ones, and checks the partition count before its listeners start. If Kafka is not running, the service stops with a clear message.

Event message: envelope and body

Every event has two parts. The envelope is the same for all event types and describes the event itself: what happened, who sent it, when, and which transfer it belongs to. The body is a nested JSON object whose fields depend on the event type. Each type has its own body with only the fields its consumers need.

How a consumer reads a message

  1. Kafka delivers the record. Spring turns the value into an EventMessage.
  2. The listener reads eventType and switches on it. Types it does not care about are ignored. Unknown types become UNKNOWN and are logged, not failed.
  3. For a type it cares about, it converts body into that type's record with EventBodyReader.
  4. It checks flowType when the service takes part in only one scenario, then calls the service method.
GlEventListener.java (excerpt)
switch (EventType.of(msg.getEventType())) {
    case COMPLIANCE_REJECTED -> {
        var b = reader.read(msg, EventBodies.ComplianceRejected.class);
        if (b.flowType() == FlowType.PARALLEL) {
            glService.reverseJournal(b.transactionRef(), b.flowType(), type, b.reason(), b.amount(), b.currency());
        }
    }
    default -> { /* not relevant for GL */ }
}
Publishing (any service)
publisher.publish(KafkaTopics.GL_EVENTS, EventType.GL_POSTING_REVERSED,
        new EventBodies.GlPostingReversed(ref, flowType, originalId, reversalId, amount, currency, reason));
// SagaEventPublisher fills the envelope (eventId, source, correlationId, causationId, occurredAt),
// adds the Kafka headers, and sends after the database commit.
Rules for changing an event

Never remove or rename a body field. Only add new fields; consumers ignore fields they do not know. A breaking change needs a new eventVersion. A body is always a JSON object, never a JSON string inside JSON.

Note

eventType, flowType and the envelope are this project's own design, not Kafka features. Kafka sees only the topic, the key, the headers and the value. The EventMessage, EventBodies and EventType classes are copied into each service, and the JSON shape is the contract between them.

05Scenario 1: Sequential

One service after another. Transaction Engine starts the Saga, GL posts the journal, FinBook records the entry.

Transaction Engine→GL Service→FinBook Service

Request: "flowType": "SEQUENTIAL". Account and Compliance ignore these events.

06Scenario 2: Parallel

Account reserves the funds first. GL and Compliance then work at the same time on the same event. FinBook runs only when both have succeeded.

Transaction Engine→Account Service→in parallelGL ServiceCompliance Service→FinBook Service

Request: "flowType": "PARALLEL". The parallel step needs no extra code: FUNDS_RESERVED is one message, and GL and Compliance each read it in their own consumer group. FinBook keeps a small finbook_join row per transaction to remember which of the two results has arrived.

Important

In the Compliance-reject case, the rejection can reach GL before GL has posted. GL then writes a CANCELLED marker instead of posting, publishes GL_POSTING_CANCELLED, and ignores the late FUNDS_RESERVED. You may see either REVERSED or CANCELLED in gl_journal. Both are correct.

How Transaction Engine decides the final status

  1. The first failure event moves the transaction from PENDING to COMPENSATING and stores the reason.
  2. Each compensation event sets a flag: gl_settled (GL reversed, cancelled or never posted) or funds_released.
  3. When every required flag is set, the status becomes FAILED. Scenario 1 needs gl_settled. Scenario 2 needs both.

Events can arrive in any order. The flags make the result the same whatever the order.

09Run and verify

Prerequisites

  • JDK 21 and Maven 3.9 or later
  • Docker Desktop (for Kafka)
  • PostgreSQL on localhost:5432, with pgAdmin or psql

Procedure

1. Create the five databases

No seed data is needed. Tables are created on first start and every row comes from your requests.

pgAdmin Query Tool, connected to the postgres database
CREATE DATABASE txn_db;
CREATE DATABASE account_db;
CREATE DATABASE gl_db;
CREATE DATABASE compliance_db;
CREATE DATABASE finbook_db;

Then set your PostgreSQL username and password in each service's src/main/resources/application.yml.

2. Start Kafka

CMD
cd D:\Choreography_SAGA\kafka
docker compose up -d

3. Start the five services

Open one terminal per service. Any start order works, because each service creates the topics it needs.

Run in each service folder
cd D:\Choreography_SAGA\transaction-engine-service && mvn spring-boot:run
cd D:\Choreography_SAGA\account-service            && mvn spring-boot:run
cd D:\Choreography_SAGA\gl-service                 && mvn spring-boot:run
cd D:\Choreography_SAGA\compliance-service         && mvn spring-boot:run
cd D:\Choreography_SAGA\finbook-service            && mvn spring-boot:run

Each console should show lines like [KAFKA] Topic 'gl-events' READY (partitions=3, replicas=1).

4. Send the six test requests

These commands work in CMD and Git Bash. In PowerShell, type curl.exe instead of curl.

10Troubleshooting

SymptomCauseFix
Service stops with "Kafka is not reachable at localhost:9092"Kafka container is not runningRun docker compose up -d in the kafka folder, then docker ps to confirm saga-kafka is up.
Service stops with "database … does not exist"Database not createdRun the five CREATE DATABASE statements in step 1.
Service stops with "password authentication failed"Wrong PostgreSQL loginFix spring.datasource.username and password in that service's application.yml.
Transaction stays PENDINGA service in the chain is not runningStart it. It reads the waiting events from Kafka and the Saga continues from where it stopped.
Log shows Cannot read body of … or Event … has no body right after upgradingTopics still hold messages in the old 1.0 format (no envelope)Run docker compose down then docker compose up -d in the kafka folder. The broker has no volume, so this starts with empty topics. These messages are skipped, not retried.
Log warns that a topic has a different partition countTopic was created earlier with other settingsKeep all five topics at the same count (3). Delete the topic in Kafka UI and restart the service, or run docker compose down for a clean broker.
Known limitation

This POC has no Outbox. If the database commit succeeds but Kafka is down at that moment, the event is lost and the transaction stays PENDING. An Outbox table is the planned fix for a production version.
